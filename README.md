# NIO Sales HRBP Data Hub —— 全国 HR 数据智能标准化与分析平台

> 可运行 Demo · 本仓库中**全部数据均为程序生成的虚构数据**，不含任何真实姓名、账号、薪资或个人信息，姓名一律脱敏展示。

本项目由两个可独立运行的 Demo 模块组成，通过「标准数据层」衔接，形成从原始数据到分析看板的完整闭环：

- **Demo 一 · Hub 数据标准化**：把各区域格式各异的原始数据，清洗成统一口径的标准数据。
- **Demo 二 · 观星看板一键生成器**：把标准数据一键生成为总部 / 区域分析看板。

核心设计判断：**AI 只负责「理解」，代码负责「执行」**。AI 输出结构化的字段映射建议，解析 / 清洗 / 校验 / 指标计算 / 图表全部由确定性代码完成，AI 不直接修改任何原始数据。

## 背景与目标

目前总部与全国区域公司在 HR 数据提报过程中，存在数据来源分散、字段命名不统一、统计口径存在差异、人工清洗工作量大、重复沟通成本高等问题。

以 Fellow Sparks 月度业绩与留存分析为例：总部需要汇总全国区域数据，按统一口径形成月度分析看板；现阶段区域侧数据存在不同表格结构及字段表达方式，总部需投入较多人工进行数据整理、字段匹配、口径确认及格式调整。月度看板目前仅有总部版本，区域尚无独立看板。

本项目采用「两步走」方案：

1. **第一步（Hub）**：将各区域格式各异的原始数据表，通过 AI 字段识别与规则清洗，统一成符合总部口径的标准数据表。
2. **第二步（观星）**：由看板一键生成器读取标准数据表，一键生成总部 / 区域分析看板。

两个模块各司其职——Hub 负责「把数据变成统一的」，观星负责「把统一的数据变成能看的」。两者之间的唯一接口是标准数据表：Hub 的产出即观星的输入，导出即可上传，无需改名或二次转换。

首期聚焦 Fellow Sparks 业绩与留存数据，后续可逐步扩展至招聘目标达成、人员规模、人效等 HR 业务数据。首期不追求一次性实现完整的智能分析与预测体系，重点验证：不同区域原始数据能否通过 Hub 自动理解与标准化、稳定输出标准数据表，以及该标准数据表能否通过观星一键生成符合总部统一口径的分析看板。

## 整体流程

```
区域原始数据表
  ↓
【Demo 一 · Hub】AI 字段识别 → 标准字段映射 → 人工异常确认 → 数据清洗与质量校验 → 标准数据层
  ↓
标准数据表（Excel / CSV）—— 两个 Demo 的「接缝」
  ↓
【Demo 二 · 观星】上传标准数据表 → 自动解析 → 一键生成 → 自包含 HTML 分析看板
```

标准数据层是两个 Demo 的「接缝」：字段名、口径、单位、列名全部固定，Hub 的产出直接作为观星的输入，导出即可上传。两个模块可独立运行、独立演示；现阶段不做系统级打通（涉及公司内部 AI 服务接口与权限，属后续项）。

## Demo 一 · Hub 数据标准化

将各区域格式各异的原始底表，统一转换为总部标准数据结构，输出标准数据表（Excel / CSV）。

**① AI 数据语义识别**
针对不同区域存在的字段名称差异，由 AI 理解字段实际业务含义，将区域字段自动映射至总部标准字段。例如「入司日期 / 入职时间 / 加入日期 / 员工入职日」经 AI 识别业务语义后，统一映射至总部标准字段。

**② 特殊字段智能处理**
对 AI 无法高置信度识别的区域特殊字段，不强制自动处理，而是进入人工确认机制。例如上海区域「XX专项新人」字段 → AI 判断可能对应「新人类型」→ HRBP 确认 → 建立「区域特殊字段 → 总部标准字段」映射关系 → 后续再次出现时自动识别。通过「AI 识别—人工确认—知识沉淀—持续复用」形成数据标准化闭环。

**③ 数据质量校验**
标准化完成后，通过规则引擎自动检查：字段完整性、数据格式一致性、重复数据、缺失数据、异常值、日期逻辑、指标计算口径、区域 / 门店名称规范性。

**④ 标准数据层与字段契约**
- 字段规模：49 个标准字段 / 6 组；其中 37 个进入下游契约，27 个为必填，缺列即本批次不可用。
- 转换规则示例：字面量空值归一、司龄量纲换算（年 ×12 → 月）、日期归一 YYYY-MM-DD、在职状态归一 1 / 0。
- 批次与版本：每次产出附快照 ID 与校准版本（SNAP-2026-08-v3 / v3 · 2026-10），保证结果可复现。
- 产出物：标准数据表可直接导出 Excel / CSV，支持区域单表与全国汇总表两种口径（schema 一致，合并即纯行拼接）。
- 首期覆盖：人员数据 + 业绩数据 + 留存数据；后续可扩展：招聘数据 + 人效数据 + 门店数据等。

### 现有实现的三个关键机制

**1. 置信度分级，AI 不假装确定**
`≥86%` 自动通过 · `50%–86%` 进入人工确认 · `<50%` 判为区域自建字段（无需映射）。低置信度字段不会被静默处理。

**2. 每一行都可人工释义，而不只是低置信度字段**
已匹配、已确认、无需映射的行同样可以复核：确认 AI 判断无误 / 修正映射 / 判为无需映射。支持写入**人工备注**（口径解释）与指定**结构化单位换算**（如「年 → 月 ×12」）。

典型场景：底表有一列「入职时长」，语义是司龄，但原始值形如 `6Y` / `7M`，而标准字段是「司龄(月)」——单位不一致，不能直接确认映射。人工写下备注并指定换算规则后，由代码执行 `6Y → 72`。**未确认换算规则时，`6Y` 会被解析为 `null` 而不是静默变成 `6`**，避免脏数据流入分析层。

**3. 三层知识库，把人工成本变成可复用资产**
- **L1** 总部标准字段（固定，区域不可修改）
- **L2** 全国通用同义词
- **L3** 区域特殊映射（人工确认后沉淀）

L3 沉淀的不只是映射关系，而是三类资产：正向映射、单位换算规则、**排除型知识**（人工确认「无需映射」的字段）。排除型知识同样会被下次命中复用，否则人工每次都要重做。

## Demo 二 · 观星看板一键生成器

上传 Hub 产出的标准数据表（固定结构 Excel）后，约 10 秒生成自包含 HTML 看板并自动打开浏览器，无需部署、无需联网、无需前端开发；交付形态为轻量本地程序，纯本地运行，生成的看板数据与样式均内联，可直接分享或归档。

基于同一套标准数据，根据使用对象自动生成不同分析视角：

- **总部视角：全国 → 区域**：全国整体表现 / 区域业绩及留存 / 区域 TOP·Bottom / 区域经营与留存散点图 / 四象限区域分析
- **区域视角：区域 → 门店**（二期规划，前提是标准化层验证通过且区域确有看板需求）：区域整体表现 / 门店业绩及留存 / 门店 TOP·Bottom / 门店经营与留存散点图 / 四象限门店分析
- 后续可进一步实现「门店 → 员工」，形成「全国—区域—门店—员工」的数据分析下钻体系。

与 Hub 的分工：Hub 解决「不同区域的数据能不能放在一起」，观星解决「放在一起以后能不能一眼看懂」；AI 负责数据理解与处理，规则与代码负责执行与校验，看板负责呈现。

## 两个 Demo 的衔接（接口实测）

- **接口定义**：标准数据表的字段名、口径、单位、必填性全部固定，构成下游输入契约；下游列名直接采用观星钦定列名（区域维度取「二级部门中文名」，保留「类型」列供 Sparks 过滤），Hub 导出即可上传，无需改名。
- **列级对齐**：31 个下游消费列全部命中（命中率 100%）。
- **行级过滤**：按「类型 = Sparks」过滤——上海单表 441 行 → 291 行；49 家区域公司拼接后 5,298 行 × 37 列 → 3,515 行。
- **交付形态**：观星已封装为「一键生成」，约 10 秒生成自包含 HTML 看板并自动打开浏览器。
- **现阶段边界**：两个 Demo 独立交付、独立演示，不做系统级打通，接口联调依赖公司内部 AI 服务与权限方案，试点通过后再评估；门店粒度暂无数据源（真实底表只到区域公司层），列为后续扩展项。

## 模拟数据端到端验证

为验证「区域原始数据表 → Hub 标准化 → 标准数据表 → 观星看板」全链路真实可用，采用合成的三家区域公司底表（刻意使用三种不同的导出方言）跑通管线：

| 区域公司 | 源表（行×列） | 标准表（行×列） | 必填就绪 | 备注 |
| --- | --- | --- | --- | --- |
| 上海 | 441×48 | 441×37 | 27/27 | 丢弃 9 列扩展字段 |
| 北京 | 288×47 | 288×37 | 25/27 | 净锁单改名 + 删除互动用户平均ΔeATV，留空标注 |
| 广州 | 170×49 | 170×37 | 27/27 | 丢弃 10 列扩展字段 |
| 合并（3 区域） | 899×— | 899×37 | — | 按 类型=Sparks 过滤后 584 行进入观星看板 |

- **① 映射覆盖率**：三家公司合计 107 个标准字段命中 auto；仅 8 列需 review（如「司龄→tenure_months」「社会工龄→social_tenure_months」按 ×12 由年换算为月），其余 unmatched 均为下游不消费的扩展列，已显式登记并忽略，不影响出表。
- **② 北京 25/27 属设计验证**：测试方言刻意将「净锁单」改名为「净锁定单数」、并删除「互动用户平均ΔeATV」——两列属下游必填契约，标准表留空并标注「缺列」，证明引擎「缺列不崩、缺失必填列不静默放过」的健壮性。
- **③ 合并后纵向拼接**为 899 行 × 37 列标准表；按「类型 = Sparks」过滤后 584 行进入观星看板，与全文所述口径一致。
- **④ 标准表导出 Excel / CSV 后**，可直接拖入「观星」生成自包含 HTML 看板，证明标准数据层作为「接缝」真实打通。

## 技术栈

- **Hub**：React 18 · TypeScript · Vite 5 · Tailwind CSS 3 · Recharts 2 · SheetJS。纯前端：Mock 数据 + 浏览器内本地处理，**无后端 / 数据库 / Docker / 消息队列**。AI 采用 Provider 抽象层，默认内置 Mock Provider；接入真实 AI 服务只需配置环境变量，且失败时自动降级，不中断演示。
- **观星**：轻量本地程序，纯本地运行，生成自包含 HTML 看板（数据与样式均内联），无需部署、无需联网。

## 本地运行

本仓库根目录的 `index.html` 是**自包含单文件版**（内联全部 JS / CSS，零外部请求）：直接下载双击即可打开，无需安装任何依赖，断网也能运行。

如需从源码运行：

```bash
npm install
npm run dev        # http://127.0.0.1:5173/
npm run build      # 生产构建
npm run verify     # 回归验证（数据 / 映射 / 口径 / 渲染）
```

## 数据安全与合规

- **数据处理边界**：一期数据在本地 / 公司内网环境处理；如 Demo 阶段需调用外部 AI 能力，将先取得公司信息安全确认并对输入数据完成脱敏，未经确认不使用真实员工数据。
- **数据脱敏**：针对员工个人信息等敏感数据（姓名、员工编号 / 域账号、手机号、薪资、离职原因原文、绩效等级等），在上传处理前进行脱敏，降低数据暴露风险。
- **可独立交付的环节**：字段字典、映射知识库、规则引擎、标准化输出流程及看板生成均不依赖外部 AI 服务，可在纯内网环境独立运行与演示。
- **数据权限模型**：总部看板所有 HRBP 均可查看；区域看板（二期规划）仅对应区域 HRBP 可查看，实现数据按区域隔离。
- **正式推广阶段**：根据公司信息安全及技术规范，进一步评估内部 AI 服务、系统接口及数据权限方案，完成合规评审后再行推广。

## 项目价值与 ROI

### 价值

- **效率**：将「复制 → 粘贴 → 字段匹配 → 数据清洗 → 口径确认 → 格式整理 → 看板制作」转化为标准化、自动化流程，减少重复性数据处理与报表制作工作。
- **标准化**：建立总部统一的数据标准、字段体系及指标口径，逐步实现全国 HR 数据的统一管理。
- **数据资产**：持续沉淀区域特殊字段及业务语义映射，形成全国 HR 数据语义知识库，随区域数据持续接入不断完善。
- **分析与管理**：总部从「收集和清洗数据」转向「分析和解决问题」，区域 HRBP 从重复填报转向业务诊断与行动跟进。最终形成：AI 负责数据理解、处理与辅助分析，人负责判断、确认与决策。

### ROI 测算（口径：制作环节）

以月度看板制作为核心测算维度。原流程制作 1 个总部月度看板约需 2 个工作日（约 16 小时）：等待业务侧数据及汇总更新约 10 小时（每月 8 号前后）、与区域 BP 沟通 / 口径确认 / 返工约 2 小时、数据制作（复制粘贴、字段匹配、清洗、格式整理）约 4 小时。新流程（Hub 标准化 + 观星一键生成）预计可将制作环节压缩至平均约 15 分钟。

关键口径：等待业务侧数据（10h）与区域 BP 沟通（2h）不计入 AI 收益——AI 无法压缩业务节奏与组织协同，ROI 仅以制作环节为口径，测算结果偏保守。以上耗时均为试点前估算值，最终以试点实测数据为准。

| 场景 | 原流程（制作环节） | 新流程（Hub+观星） | 节省工时 |
| --- | --- | --- | --- |
| 单次看板制作 | 4 小时 | 约 15 分钟 | 约 3.75 小时（人工操作效率提升约 62.5%） |
| 总部试点（按年 · 12 次） | 48 小时 | 3 小时 | 45 小时 ≈ 5.6 人天 ≈ 0.26 人月 |
| 区域推广（49 区域 · 情景测算） | 2,352 小时 | 147 小时 | 2,205 小时 ≈ 12.7 人月（避免重复建设） |

注：人月 = 21.75 人天；区域推广为情景测算（假设区域确有看板需求）；本表数据为试点前估算值，最终以试点实测为准。

### 长期发展路径

第一阶段：数据标准化（解决「不同区域的数据能不能放在一起」）→ 第二阶段：分层分析（总部看区域，区域看门店，门店看员工）→ 第三阶段：智能诊断（从结果指标进一步分析异常及原因）→ 第四阶段：风险预测（留存风险、招聘达成、人效及人才供需预测）。
